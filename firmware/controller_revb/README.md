# Rev B 制御基板ファームウェア（STM32G431CBT6 / STM32CubeIDE）

状態: **初版・実機未検証（2026-10-15）**。書き込み・通電・ロボット接続はまだ一度もしていません。
ロジック部分はPC上のテスト（282項目）が通り、ST純正HALに対してARM向けのビルドとリンクが通ることを確認済みです（Flash 22 KB / RAM 2 KB）。
`SupercapRevB.ioc` はCubeMXの例題の書式に合わせて手で書いたもので、**CubeMXで開いて生成できるかは未確認**です。

## 何をするファームか
- PMのシャーシ出力から取る**入力電力**を、審判システムのシャーシ電力上限以下に保ちながら、LM5176でバンク（ノード）を充電します。
- 電力上限の取得元（優先順）: 基板の審判UART（0x0201/0x0202） → ロボットからのCAN 0x210 → 既定値 40 W。
- 緩衝エネルギーが40 Jを下回ると、1 Jあたり1.5 W ずつ目標を下げます。
- 満充電付近（ノード25.5 V以上）では、バンク基板のクランプが逃がせる電流が小さいため、バンクへの充電電流を平均0.5 Aに抑えます（EN_CHGを100 ms周期でオン/オフ）。
- 保護はハード（入力OV・ノードOV比較器、イネーブル既定OFF）が主で、ファームは起動順序、過熱、過電流、短絡、リトライを担当します。
- **短絡検出**: 制御基板v3はLM5176のヒカップを無効にしているため（MODE 200 kΩ）、ノードが短絡してもハードは止まらず、谷電流制限（約5.5〜7.9 A）で流し続けます。そこでファームが、ノードが10 V未満のあいだ、実際にスイッチングしている時間1秒ごとにノード電圧が0.3 V以上上がっているかを見ます。上がらなければ充電を止めます（故障0x40）。5秒後に再試行し、3回続けば電源を入れ直すまで停止したままにします。空の5 Fバンクは最小の電流制限でも約1.1 V/sで上がるので、正常な充電では止まりません。

## STM32CubeIDEでのプロジェクト作成
1. CubeIDEで **File → New → STM32 Project from an Existing STM32CubeMX Configuration File (.ioc)** を選び、`SupercapRevB.ioc` を指定する。プロジェクトの場所は**このフォルダ**（`firmware/controller_revb`）にする。
2. コード生成後、`Core/Src/main.c` に次の3行を入れる（手でも、`tools/patch_main.ps1` でも可）。
   - `/* USER CODE BEGIN Includes */` の下: `#include "sc_app.h"`
   - `/* USER CODE BEGIN 2 */` の下: `sc_app_init();`
   - `/* USER CODE BEGIN 3 */` の下（while(1)の中）: `sc_app_loop();`
3. ビルドする。`sc_*.c` は `Core/Src` にあるので、インクルードパスの追加は不要。
4. CubeMXで設定を変えて再生成しても、`sc_*` ファイルとUSER CODE内の3行は残る。

生成物（Drivers/、main.c など）は `.gitignore` でリポジトリに入れない方針です（Rev Aと同じく、ST配布物を公開リポジトリにコピーしないため）。

## CAN（1 Mbps、標準ID、リトルエンディアン）
| ID | 方向 | 内容 |
|---|---|---|
| **0x211** | 基板→ロボット 100 Hz | [0-1] 入力電圧×100、[2-3] コンデンサ（ノード）電圧×100、[4-5] 入力電流×100、[6-7] 目標入力電力×100（**今のTaobao基板と同じ形式**） |
| 0x212 | 基板→ロボット 20 Hz | [0] 状態、[1] 故障ビット、[2-3] バンク電流×100（int16、+＝充電）、[4-5] 温度×10、[6] 残エネルギー%、[7] フラグ |
| 0x210 | ロボット→基板（任意） | [0-1] シャーシ電力上限×100 [W]。審判UARTが無いときだけ使う |

**ロボット側（Teensyコード）について**: 0x211の受信処理はそのまま使えます。ただし `const.h` の `capacitor_full 2000`（20.00 Vを100%）は、10S構成だと満充電が約26.2 Vになるので `2620` 前後に直す必要があります。

状態: 0 BOOT / 1 IDLE（待機） / 2 START / 3 CHARGE / 4 FAULT。
故障ビット: 0x01 入力過電圧、0x02 ノード過電圧、0x04 過熱、0x08 入力過電流（ラッチ、電源再投入で解除）、0x10 センサー異常、0x20 起動時の読み返し異常、0x40 短絡（充電してもノード電圧が上がらない。3回連続でラッチ）。
フラグ: 0x01 審判データ有効、0x02 CAN指令有効、0x04 満充電付近、0x08 PGOOD、0x10 PMOS_EN、0x20 NODE_OK、0x40 充電器オン。

## LED
- 緑: 待機中は1秒ごとに短く点滅、充電中は点灯、満充電付近は速い点滅。
- 赤: 故障中、故障ビットの位置+1回の点滅を2秒ごとに繰り返す（1回＝入力過電圧、2回＝ノード過電圧、3回＝過熱、4回＝過電流、5回＝センサー、6回＝起動異常、7回＝短絡）。

## 初回の確認手順（推奨）
1. **電力段なしで**: 3.3 Vだけで起動し、CubeIDEのLive Expressionsで `tel` を見る（`sc_app.c` の静的変数）。VDDAが3.3 V付近、温度が室温付近であること、EN_CHG/EN_PMOSが0のままであることを確認する。
2. **電流制限付きの安定化電源**（24 V、1 A）を入力に、バンクの代わりに小容量の負荷（例: 100 Ω）をつなぐ。電圧・電流の表示値をテスターと比べ、`sc_config.h` の校正値か `sc_cal_t` を合わせる。
3. DACと実際の入力電流上限の関係を測る（`SC_VBE` の合わせ込み）。
4. 審判UARTを接続し、0x212のフラグ0x01（審判データ有効）が立つこと、目標電力（0x211の[6-7]）が上限−2 Wになることを確認する。
5. バンクを接続した充電は、電源の電流制限を下げた状態から始める。

デバッガで止める（ブレークポイント）と、既定ではウォッチドッグで約200 ms後にリセットされ、充電は停止します（安全のため）。止めてデバッグしたいときは、電力段に通電しない状態で `SC_DEBUG_FREEZE_IWDG` を1にします。

## 未検証・要確認
1. `.ioc` をCubeMXで開いたときに、設定がすべて意図どおり読み込まれるか（特にADCのランクとオーバーサンプリング、FDCANのクロック源PCLK1）。
2. LM5176のISNSしきい値（50 mV）、Q3のVbe、DAC→電流上限の関係。現状はモデル値で、PIの補正（最大±1 A）で誤差を吸収する設計。
3. DACで下げられる電流上限は約1.2 A（約28 W）まで。それ以下の目標はオン/オフで平均を合わせるため、入力電力が脈動する。審判の電力計測がこれをどう扱うかは未確認（R7 6.8 kΩを小さくすればDACだけで下げられる範囲が広がる）。
4. 満充電付近のオン/オフ制御で、バンク基板のクランプを超えないこと（実機で各セル電圧を測って確認）。
5. 審判システムの電力上限が今季のルールでいくつになるか、既定値40 Wが妥当か。
6. CM01との関係（電流方向・電圧の見え方）は実機で確認する。
7. 短絡検出のしきい値（10 V、1秒、0.3 V）。バンクを外してシャーシ負荷だけをつないだとき、または大きな負荷がノードにかかっている低電圧時に誤検出しないかを実機で確認する（`sc_config.h` の `SC_SHORT_*`）。
